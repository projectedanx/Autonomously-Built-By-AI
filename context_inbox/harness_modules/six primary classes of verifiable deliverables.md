In agent-first integrated development environments like **Google Antigravity** and terminal-based orchestrations like **Gemini CLI** and **Jules**, the shift from passive code generation to autonomous agency is anchored by the creation of **verifiable deliverables (Artifacts)**. Rather than forcing a human to parse raw, unconstrained terminal outputs or blindly execute unchecked code, autonomous agents package their reasoning and output into structured, verifiable formats. 

These deliverables serve as a cryptographic and structural audit trail, allowing developers and system frameworks to programmatically verify, simulate, and check execution states before committing any mutations to the codebase.

### I. Architectural Taxonomy of Verifiable Deliverables

Based on the project files and operational workflows of contemporary agentic engines, agents generate **six primary classes of verifiable deliverables** across their lifecycle:

```
  [ STRATEGIC ]           [ OPERATIONAL ]          [ FUNCTIONAL ]
   PRD / Spec              Decompositions           Visual Diffs
  (PRD.md / SOPs) ───►  (Task Lists / TODOs) ───►  (Side-by-Side)
                                                          │
                                                          ▼
  [ TELEMETRIC ]           [ RUNTIME ]             [ EXECUTABLE ]
   OpenTelemetry            Assets / Media          Unit Tests
   (OTEL Traces)  ◄───  (Screenshots / Video) ◄─── (Jest / Pytest)
```

#### 1. Strategic & Specification Artifacts (The Intended State)
Before writing code, agents translate vague user requests (such as a list of raw thoughts in a `features.md` file) into formalized specifications. These documents align the agent's proposed architecture with the user's mental model.
*   **Product Requirements Documents (PRDs):** Structured Markdown specifications (`PRD.md`) outlining strict functional requirements, non-functional boundaries, technology stacks, and out-of-scope boundaries.
*   **Standard Operating Procedures (SOPs):** Reusable playbook frameworks generated by agents (often as project-level `GEMINI.md` context files) that standardize coding styles, dependency rules, and testing parameters for themselves and peer worker agents.

#### 2. Decomposition Artifacts (The Execution Path)
To prevent "vibe coding" drift where an agent wanders off-task, the system requires the model to formally decompose complex intents into discrete, verifiable subtasks.
*   **Structured Plans:** Multi-step strategic outlines specifying exactly which files must be examined, which parameters need validation, and what tools are required to achieve the goal.
*   **Dynamic TODO Trackers:** Self-updating checklists (e.g., `- [ ] pending`, `- [/] in progress`, `- [x] done`) that register state transitions during long-running tasks, allowing users or supervisor engines to audit execution velocity and pause loops if necessary.

#### 3. Structural Code Diffs (The Proposed Mutation)
To avoid silent and destructive filesystem changes, modern harnesses enforce a strict separation between planning a code edit and applying it.
*   **Side-by-Side Diff Files:** Temporary file buffers mapping the delta between the current workspace and the proposed state. Inside companion environments like VS Code, these trigger native visual diff windows, allowing developers to review, edit, or reject the exact patch line-by-line before execution.
*   **Git Diffs & Draft Pull Requests:** Asynchronous agents like **Jules** or integrated GitHub Action runners automatically clone repositories to cloud VMs, compile changes, run build diagnostics, and package the finalized solution into a fully documented **GitHub Pull Request** with a detailed commit summary.

#### 4. Executable Test Suites (The Logical Validation)
Vibe coding often produces code that compiles but fails logical constraints under edge cases. Agents generate test deliverables to programmatically verify code behavior.
*   **Automated Test Specs:** Standardized test suites written in frameworks like Jest, Pytest, or JUnit. Under a strict **Test-Driven Development (TDD)** loop, the agent generates a test that reproduces a reported bug or verifies a new feature, running the test to establish a baseline failure (Red) before writing the corrective implementation to pass the test (Green).
*   **Coverage & Linting Reports:** Formatted diagnostic logs generated by executing testing or static analysis tools (like Ruff) to confirm that the proposed changes did not degrade codebase test coverage or introduce style regressions.

#### 5. Runtime & Media Deliverables (The Visual Evidence)
For frontend development, full-stack visual tools, or complex pipeline automations, text-based logs are insufficient. Agents generate multimodal assets to verify runtime behavior.
*   **Live Application Screenshots:** Captured snapshots of sandboxed web pages or mobile views allowing vision-enabled models to check layout consistency, color contrast, and styling alignment against visual design guides.
*   **Interactive Browser & Video Recordings:** Full-motion video or interactive replay recordings showing an agent's direct manipulation of web applications inside containerized browsers (like Chrome DevTools MCP or browser execution runtimes) to verify script flows and complex visual states.
*   **Generated Design Assets:** Vector graphics, image assets, or localized media files (such as database-derived CSV sheets) created during processing tasks to satisfy business requirements.

#### 6. Protocol-Level Envelopes (The Interoperability Standard)
When agents interact across distributed systems or delegate tasks to specialized sub-agents, they encapsulate their outputs into standardized, machine-readable schemas defined by collaborative standards.
*   **A2A Artifact Objects:** Under the **Agent-to-Agent (A2A)** protocol, standardized outputs are delivered inside structured JSON envelopes that pair the payload (the generated file or result) with explicit, metadata-driven safety, lint, and compiler metrics.
*   **MCP Resource Declarations:** Under the **Model Context Protocol (MCP)**, custom-built tools expose resources (such as structured database query results, live calendar schedules, or Google Docs files) as type-safe schemas that can be cleanly consumed by orchestrators.

### II. The Architecture of Verifiability: Gating and Control Loops

An artifact is only truly "verifiable" if the harness provides deterministic, observable environments to grade its accuracy. This is managed through three primary control systems:

| Verification Metric | Target Deliverable | Verification Mechanism / Oracle |
| :--- | :--- | :--- |
| **Syntactic Integrity** | Structural Code Diffs | The client-side runtime executes local linter binaries (e.g., `npm run preflight`, `ruff check`). |
| **Behavioral Alignment** | Executable Test Suites | The TDD runner executes tests in a closed sandboxed container, evaluating assertions against the generated payload. |
| **Stateful Coherence** | Thought Signatures | The Vertex AI / AI Studio API captures the model's cryptographic `thought_signature` and requires it to be round-tripped with tool execution responses to prevent planning amnesia. |
| **Environmental Containment** | Shell Commands & Writes | A strict **User Confirmation Policy** evaluates the severity risk of the action (YOLO, Safe, or None modes) and pauses the execution loop for human-in-the-loop validation. |
| **Telemetric Compliance** | API and Tool Metrics | The harness pipes structured logs, token counts, latency metrics, and error rates to an **OpenTelemetry (OTel)** daemon, verifying usage budgets. |
