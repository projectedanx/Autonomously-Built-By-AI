### Reverse Engineering Google Antigravity: Systems Engineering Specification for Agent-First IDE Harnesses

To architect or reverse engineer a production-grade AI Harness capable of mirroring an **agent-first integrated development environment (IDE)** like Google Antigravity, we must move beyond the paradigm of simple chat completion overlays and autocompletion scripts. Traditional AI environments operate on a "suggest-and-paste" model. In contrast, an agent-first IDE functions as an autonomous, multi-agent workspace runtime environment that manages parallel task queues, coordinates with local and remote filesystems, executes sandboxed runtime tests, and performs real-time browser verification loops.

---

### Phase I: Automated Discovery and Constraint Mining

 Vague natural language requirements hide catastrophic edge cases, such as "doom loops" or unintended filesystem modification. To build a safe, robust, and highly aligned agent harness, we categorize core operational constraints into **Hard Boundaries (Invariants)** and **Soft Targets (Optimizable Goals)**.

#### 1. Hard Boundaries (Invariants)
*   **The State Preservation Invariant (Thought Signatures):** In multi-turn tool calling, the orchestrator harness *must* capture, serialize, and round-trip the cryptographic `Thought Signature` generated by reasoning models (like Gemini 3 Pro) with every subsequent tool response. Failure to transmit this signature causes "amnesia" or context drift, forcing the model to lose its planning trajectory and restart the task.
*   **The Strategist-Implementer Partition:** To mitigate the "lazy implementer" trap (where the agent writes raw code without verifying codebase syntax or dependencies), the harness must enforce a strict state machine split.
    1.  **Plan Mode (Read-Only/Strategist):** The agent explores the repository tree, reads configuration specs (`GEMINI.md` or `CLAUDE.md`), and outputs an implementation plan (PRD/Artifact). *Code editing tools are statically and dynamically disabled*.
    2.  **Human Gate (Verification):** The plan must receive user approval.
    3.  **Execute Mode (Implementer):** The agent runs the code modifications, executes tests, and verifies outputs.
*   **Containment Isolation (The Execution Sandbox):** Any tool invocation capable of modifying files, changing environmental paths (e.g., `JAVA_HOME`), running compilers, or executing shell binaries *must* be confined to an isolated container (e.g., Docker `gemini-cli-sandbox`, Podman, or OS-level sandboxes like macOS Seatbelt).
*   **Shadow Rollback and Falsification (Version Control Integrity):** The harness must maintain a parallel, immutable version control tracking state—such as a Git shadow repository or temporary worktrees—prior to any file mutation tool execution. Reverting a checkpoint must be a non-destructive state reconstruction. *Direct manual file path deletion on rollback is strictly prohibited to prevent data loss*.

#### 2. Soft Targets (Optimizable Goals)
*   **Context Density optimization:** Balancing the 1M+ token context window of reasoning engines against the latency-accuracy trade-off. pre-loading an entire repository wastes tokens and degrades reasoning focus. The system should prioritize **Just-In-Time Context Loading**, utilizing lightweight file indexing (`glob`, `grep`, `tree-view` summaries) to inject only high-relevance source code files on demand.
*   **Tiered Model Delegation (Cost-to-Reasoning Ratio):** High-level architectural planning, final synthesis, and safety audit tasks are allocated to the most capable models (e.g., Gemini 3 Pro with high `thinking_level`). Straightforward, high-throughput executions (e.g., boilerplate generation, syntax cleanup) are delegated to faster, lower-cost models (e.g., Gemini 2.5 Flash).

### Phase III: Parametric Trade-off Modeling

Designing an agentic IDE requires managing a critical multidimensional tension between **Execution Velocity** and **Alignment Accuracy**.

```
                     High Alignment Accuracy
                     [Plan-First / TDD / Human Gate]
                               ▲
                               │     * (Target Harness Balance)
                               │    /
                               │   /  Feasibility Frontier (Pareto Curve)
                               │  /
                               │ /
                               │/
                               └────────────────────────► High Execution Velocity
                                                         [YOLO / Direct Shell Access]
```

#### 1. Parametric Frontier Variables
*   **$V_{exec}$ (Execution Velocity):** Measured as tasks resolved per unit time. High velocity is achieved by skipping planning phases, disabling human-in-the-loop (YOLO mode), and granting raw shell capabilities.
*   **$A_{align}$ (Alignment Accuracy):** Measured as the percentage of codebase commits that adhere perfectly to standard design configurations (e.g., `GEMINI.md` architectural files) and pass CI test suites.
*   **$D_{spec}$ (Specification Density):** The byte size of the instructional ruleset injected into the system prompt.
    *   *High Density ($D_{spec}$):* Detailed rules defining directories, conventions, and style constraints. *Guarantees style adherence, but consumes context tokens and increases cognitive degradation*.
    *   *Low Density ($D_{spec}$):* Zero-shot raw requests. *Maximum context window space for workspace codebase files, but high risk of style drift*.

#### 2. Feasibility Frontier Formula
We model the system's operational efficiency as:

$$\eta = f(V_{exec}, A_{align}) = \frac{A_{align} \cdot \log(D_{spec})}{Latency_{total}}$$

When $V_{exec}$ is pushed to the limit via unconstrained YOLO shell execution, $A_{align}$ drops exponentially due to unhandled exceptions, syntax errors, and missing package dependencies. Conversely, enforcing strict TDD and Plan-Execute-Verify cycles reduces velocity but pushes $A_{align}$ to the frontier of production-grade software delivery.

### Phase IV: Continuous Falsification and Edge-Case Stress Testing

An AI Harness must survive bad code suggestions and adversarial environments. We stress-test the specification by modeling the dynamics of three fatal failure modes:

#### 1. The "Doom Loop" (Failing Build Cycles)
*   **Trigger:** The agent encounters a persistent build failure (e.g., an unresolved reference in a monorepo).
*   **Failure Signature:** Lacking a high-level abstraction tool, the agent calls raw shell commands (`run_shell_command`) repeatedly, changing minor syntax variations or package versions. This results in massive token consumption, context window exhaustion, and zero resolution.
*   **Mitigation Strategy:** Implement a maximum execution loop limit (`maxSessionTurns` or `max_iterations`). If the compiler/test oracle fails twice consecutively with identical stderr outputs, the harness must trigger an **Escape Hatch** that interrupts execution, compresses history, and requests clarification or human steering.

#### 2. Rollback Destruction
*   **Trigger:** The user invokes `/restore` or a rollback operation after an agent has failed a complex multi-file refactoring task.
*   **Failure Signature:** The restoration engine deletes newly created directories or erases uncommitted user edits because it relies on simple file diffing without verifying active workspace state.
*   **Mitigation Strategy:** Bind all checkpoint snapshoting directly to Git-level trees. The rollback tool should execute a git checkout/reset command strictly confined to the project root index. If uncommitted changes exist, the harness must prompt the user to stash their local state before attempting restoration.

#### 3. Indirect Prompt Injection (Data Exfiltration via Tool Pipeline)
*   **Trigger:** The agent is asked to analyze an untrusted asset (e.g., summarize a pull request, review an issue, or read a calendar event) containing hidden prompt injection instructions.
*   **Failure Signature:** The adversarial payload instructs the agent to ignore its system prompt and use its native `WebFetch` or `curl` tools to exfiltrate database keys or repository source code to an attacker's server.
*   **Mitigation Strategy:** Enforce **Deterministic Runtime Policies (Layer 1)**. The policy engine must intercept outgoing HTTP requests. If the agent attempts a write or data-sending action after reading untrusted files, the transaction must be blocked automatically unless an explicit, out-of-band user confirmation (Human-in-the-Loop) is granted.

### Phase V: Specification Feasibility Simulating

We model the harness's requirements matrix as a dynamic system with state transitions governed by a closed-loop controller.

```
                  ┌──────────────────────────────┐
                  │                              │
                  ▼                              │
┌──────────────────────────────────┐             │
│       Reasoning Model (LLM)      ├─[Thought_Sig]────┐
│ (Analyzes Code, Formulates Plan) │             │    │
└────────────────┬─────────────────┘             │    │
                 │                               │    │
                 ├─[Requires Tool]               │    │
                 ▼                               │    │
┌──────────────────────────────────┐             │    │
│      Verification Engine         │             │    │
│  (Validates Plan / Review Diff)  │             │    │
└────────────────┬─────────────────┘             │    │
                 │                               │    │
                 ├─[Approved by User]            │    │
                 ▼                               │    │
┌──────────────────────────────────┐             │    │
│      Execution Environment       │             │    │
│ (Isolated Sandbox: Docker/PTY)   ├─[Stdout/Err]┘    │
└────────────────┬─────────────────┘                  │
                 │                                    │
                 └─[Verifies Build/TDD Outputs]       ▼
                        ├─────────────────────────► [VCS Commit]
                        └─[Fails Tests]───────────► [Self-Correction Loop]
```

1.  **Orchestrator Feed-Forward Loop:** The prompt, workspace tree index, and active `GEMINI.md` specifications are fed into the LLM.
2.  **Tool Interceptor Feedback Loop:** The LLM's response is evaluated. If it's a tool request, the harness routes execution to specific sandboxed APIs.
3.  **Self-Correction Cascade:** If the build compiler or test suite returns an error code, the exact stderr trace is captured. The harness wraps this output as an `Observation` payload, couples it with the `Thought Signature` token, and feeds it back into the model's next reasoning cycle. This dynamic loop continues until the system converges on a valid build or hits the loop-break boundary.
